# 稳定性排查与加固（2026-10-15）

起因：用户测试时遇到一次**程序突然退出**，要求排查代码健壮性，
特别是"音视频解码错误导致的退出"，并给出进一步增强稳定性的建议。

本文记录：排查了哪些地方、发现了什么、修了什么、还剩哪些建议。

---

## 1. 最可能的元凶：从 worker 线程直接操作 UI

**位置**：`MainWindow::setupTimeline()` 里给 `waveBuilder_` 设的两个回调。

`WaveformBuilder` 用的是 **`std::thread`**（4 个 worker），不是 `QtConcurrent`。
它的 `progressCb_` / `errorCb_` 是在 **worker 线程**里被调用的，而回调体里写了：

```cpp
if (timeline_) timeline_->update();        // QWidget，只能 GUI 线程碰
appendLog(...);                            // 直接操作 infobox（QTextEdit）
rebuildCutWaveform(cutToken_);             // 读 UI 状态 + 再起后台任务
```

Qt 的规则是**任何 QWidget 都只能在 GUI 线程使用**。从后台线程调 `update()` /
`insertHtml()` 是未定义行为：绝大多数时候看起来没事，偶发就是直接崩，
而且崩在哪一行、什么时机完全随机 —— 正好对应"用着用着突然没了"这种症状。

**为什么之前没暴露**：时序巧合。波形算得快的时候，那几行可能正好赶在
GUI 线程空闲时执行完；一旦同时有别的任务占用（比如正在解码、正在取缩略图），
Qt 内部的状态就可能对不上。

**修法**：两个回调的 lambda 本体一行都不碰 UI，全部
`QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 丢回 GUI 线程再做，
并带 `QPointer` guard + token 校验。

> 顺带核对过：其余 8 处 `QtConcurrent::run` 的后台块都是干净的
> （只做计算，UI 操作都走 `invokeMethod`），就这一处是 `std::thread` 漏了。

## 2. 第二个元凶：播放时帧回调没有背压

播放线程每解一帧就 `QMetaObject::invokeMethod` 投一个含 `QImage` 的 lambda 给
GUI 线程。GUI 一忙（比如同时有 4 个线程在算整轨波形），**这些事件会排起队来**。

一张 1080p 的 `QImage` = 6 MB。积压几十帧就是几百 MB，几百帧就是上 GB ——
结局不是卡死就是被系统杀掉，而用户看到的只是"程序突然没了"。

**修法**：`pendingFrames_` 原子计数，投递前 +1、GUI 线程执行时 −1，
待处理 ≥ 3 帧就直接丢掉这一帧。**播放宁可掉帧，也不能让内存失控。**
`stopPlayback()` 里归零，且计数减到 0 就夹住不让它变负
（否则下一轮播放要白丢好几帧才恢复正常）。

## 3. 线程里的异常 = 进程直接消失

`FramePlayer::threadMain` 和 `WaveformBuilder::workerMain` 都**没有 try-catch**。
解码、sws 缩放、`std::vector` 分配都可能抛异常（损坏文件、异常分辨率、内存不足）。
异常一旦逃出线程函数，C++ 运行时直接 `std::terminate()` —— 整个进程瞬间消失，
**没有日志、没有崩溃对话框、没有任何提示**。这跟用户描述的"退出"完全吻合。

**修法**：两个线程入口各包一层 `try { ... } catch (...) { ... }`，
捕获后安静地按"播完了/这段不算了"处理。

## 4. 其余修掉的隐患

| # | 位置 | 问题 | 修法 |
|---|---|---|---|
| 1 | `MainWindow::toQImage` | 只查了 `rgb.empty()`，没校验数据量；尺寸对不上就是**越界读** | 校验 `rgb.size() >= w*h*3`，并限制最大 16384×16384、`image.isNull()` 也判掉 |
| 2 | `FramePlayer::close()` | 不先 `stop()` 就释放 `video_`/`audio_`，播放线程还在用它们 → **use-after-free** | `close()` 开头先 `stop()` |
| 3 | `FramePlayer::pumpAudio` | 音频包无时间戳时 `startSec = -1`，`audioSec_` 变负、循环永不退出，**一口气读完整个文件** | 无时间戳时按"接上一段"估算；并加 512 次硬上限 |
| 4 | `AudioDecoder::decodeNext` | swr 输出未钳制，`produced` 超预期会写穿缓冲区 | `used += std::min(produced, space)` |
| 5 | `FrameGrabber::decodeNext` | 损坏文件时坏包循环会一直读到文件尾，界面不崩但 CPU 跑满 | 连续 300 个坏包就放弃并报错 |
| 6 | `FrameGrabber::grabAt` | seek 失效/时间戳乱掉时会一路解到文件尾（长视频几万帧） | 1500 帧上限，超限用已拿到的最后一帧 |
| 7 | `FrameGrabber::convertFrame` | 异常分辨率让 `resize` 抛 `bad_alloc` | 尺寸合法性 + 上限检查 |
| 8 | `MainWindow::applySnappedRange` | 吸附把区间吸反了（关键帧稀疏/损坏文件时真的会）**只打日志，照样把倒挂区间写回去** → 目前时长负数、可拿负区间去编码 | 检测到倒挂就保持原选择不变 |

第 8 条是**用损坏文件实测出来的**：污染视频的关键帧表异常，吸附后变成
`起点=5.000 终点=2.000`。修完变成保持 `2.300 ~ 4.700` 原值。
（`cutFile()` 本来就有 `end <= start` 的校验兜底，所以不会真的去编码。）

## 5. 加上的诊断能力：日志落盘 + FFmpeg 报错接入

这次"不知道是什么原因"，下次就得能查。

- **程序日志**：`main.cpp` 装 `qInstallMessageHandler`，所有 Qt 日志写一份到
  `logs/LRConvert.log`（exe 同级；写不进去就退回系统临时目录）。
  超过 2 MB 重新来一份。**每条立即 `fflush`** —— 崩了也要留下最后那几行，
  而那往往正是最接近现场的部分。
- **FFmpeg 自己的报错也接进来**：新增 `FfmpegApi::setLogSink()`，
  把 `av_log_set_callback` 桥到程序日志。解码器抱怨了什么、哪个流坏了、
  硬件编码器为什么不可用，以前只飘在 GUI 程序看不见的 stderr 里，现在进日志文件。

  ⚠ **这里有个坑**：FFmpeg 的 `av_vlog()` 拿到回调**直接就调**，
  级别过滤只存在于它的默认回调里。自定义回调必须自己判断 `level`，
  否则硬件探测那堆 `Loaded lib: nvcuda.dll` 会全涌进来 ——
  实测一次启动刷出 **56083 条**。
- **限流**：坏文件会源源不断报同一个错，前 100 条照实记，之后每 100 条汇总一次。
  修完 56083 → **156 条**，日志 21 KB。
- **`app.exec()` 兜底**：包 try-catch，真漏出异常时弹框说明 + 写日志，
  而不是 `std::terminate()` 静默消失。

## 7. 还没做的进一步建议

按性价比排序，都不是必修，视需要再上：

1. ~~**崩溃转储**：装 `SetUnhandledExceptionFilter` 在崩溃时写 minidump。~~
   **已做**，见 §8 与 §9。
2. **日志按天轮转 + 保留最近 N 份**：现在只按 2MB 截断，长期用会覆盖历史。
3. **播放与波形错峰**：导入后的头几秒 CPU 是打满的（4 worker + 解码）。
   可以让波形在播放开始后自动降优先级（减到 1~2 个 worker）。
4. **长视频内存上限**：现在是 400 点/秒，2 小时视频 = 288 万点 ≈ 5.8 MB，
   可以接受；但若将来提高密度，要给 `allocate()` 加总量上限。
5. **硬件编码器探测超时**：探测 nvenc/qsv/amf 是在后台线程做的，
   个别驱动上可能卡住，建议加超时（目前没观察到）。
6. **`FramePlayer::stop()` 的 join 无超时**：理论上播放线程一定会在
   一帧时间内退出（最坏等一个 `write` 的 40ms 超时），暂不需要；
   若将来在循环里加了更长的阻塞操作，就得给 join 加上限。

# 8. 遇到解不出的块该怎么办（2026-10-15 续）

上面几节防的是"程序自己写错"，这一节防的是**输入数据本身是坏的**。
音视频文件局部损坏是家常便饭：**解码错误不是异常，是常态输入**。
一个坏包就终止整个流程，等于把"数据质量问题"错误升级成了"程序失败"。

## 8.1 先分清楚坏在哪一层

| 层级 | 表现 | 应对 |
|---|---|---|
| **包级**（最常见） | `avcodec_send_packet` 返回负错，日志刷 `error while decoding` | 跳过这一个包继续读；**只有连续几百个都坏**才判定整条流报废 |
| **帧级** | 解出来了但花屏、绿块、撕裂；音频爆音 | 交给解码器做错误隐藏；视频沿用上一帧，音频做丢包隐藏 |
| **流级** | 连续失败、时间戳全乱、容器索引损坏 | 熔断停止空转，降级（只播画面 / 只播声音 / 波形留空洞）并记日志 |

## 8.2 同一个坏块，四个功能四副态度

区别只在于"用户能不能接受你的猜测"：

- **播放**：目标是别断 —— 丢帧、沿用上一帧、音频补一段，**绝不因一帧失败停下**
- **定位取帧**：目标是给个画面 —— 允许退回上一帧或最近关键帧，宁可不精确
- **波形索引**：目标是别撒谎 —— 算不出来就留空洞，**绝不能当成"静音"画成平线**（两种含义）
- **截取导出**：目标是产物可信 —— 这是唯一不能自作主张的场景，坏块不能静默丢掉

## 8.3 落地的四条改动

### (1) 播放循环区分"播完了"和"这一帧坏了"

原先 `FramePlayer.cpp` 里是 `if (!video_.grabNext(...)) break;`，注释还写着"读完了"。
于是**解码失败和正常播完走同一条路**：播放到坏块处就"自然结束"，
用户看到的只是播放莫名停住。

改法：`FrameGrabber::DecodeResult{ Ok, EndOfStream, Error }` 三态，播放循环里：

- `EndOfStream` → 真结束
- `Error` → **沿用上一帧**：把上一张好画面按新时间戳再送一次，时间继续走，
  等坏区过去自然接上；连续补救超过 1.5 秒才放弃

"沿用上一帧"原本要每帧多拷 6 MB（1080p）。改法是把 `FrameData::rgb` 换成
`shared_ptr<const vector<uint8_t>>`：正常帧 move 一次进去，补救帧只多一个引用，
**零拷贝**。

音频侧同理：`Error` 时补一段丢包隐藏音（PLC），连续 20 次才放弃音轨、只播画面。
PLC 的做法是把上一段 PCM 的尾音（20 ms）搬过来线性衰减到 0 —— 比硬切静音自然，
不会在坏块处留下"咔哒"。

### (2) 熔断计数改会话级，坏区直接跳过去

原来 `badPackets` 是 `decodeNext()` 里的**局部变量**，每次调用都从 0 数起。
碰上"中间一大段全坏"的文件，外层 1500 帧循环会一遍遍进来、每遍读几十个坏包
再退出 —— 不死循环，但白白烧 CPU，界面看着像卡住。

改成成员级 `badRun_` 之后：连续坏包在**整个播放过程**里累计，
攒到 64 个就 `avformat_seek_file` **直接向前跳 1 秒**越过这片坏区
（最多跳 20 次，防止来回横跳）；跳不动（没时间戳 / 超上限）才在 300 个时认命。

### (3) 坏块统计要有出口

画面是靠补救撑下来的这件事，必须让用户知道，不能装作一切正常：

- 导入取帧后：`⚠ 这份素材有 N 个损坏的数据包，取帧时已跳过`
- 播放结束后：`⚠ 素材存在损坏，播放已尽量补救：视频跳过 N 个损坏包、M 段画面沿用上一帧……`
- 冒烟接口 `smokeDamageState()`，可自动核对

### (4) 解码器端的两个旋钮

```cpp
codec_->error_concealment = FF_EC_GUESS_MVS | FF_EC_DEBLOCK;
```

让解码器主动补残缺宏块，坏块处是"局部糊一块"，而不是整帧变绿或整帧丢失。

> ⚠ **千万不要设 `AV_EF_EXPLODE`**：它会把轻微错误当致命，
> 本来还能出画面的帧也一并返回失败，画面反而烂得更快。
> `err_recognition` 保持默认的 `AV_EF_DEFAULT` 就好。
>
> 另外 `FF_EC_GUESS_COS` 在现在的 FFmpeg 头文件里已经改名为 `FF_EC_GUESS_MVS`
> （踩过一次编译错误）。

# 9. 崩溃转储（minidump）

try-catch 只能拦 C++ 异常，**拦不住空指针解引用、栈溢出、堆损坏**这类
Windows SEH 错误 —— 那正是"程序突然没了"最常见的成因，而且日志里连最后一行
都留不下来。

新增 `src/platform/CrashDump.{h,cpp}`，覆盖三条路：

| 路径 | 覆盖 |
|---|---|
| `SetUnhandledExceptionFilter` | 访问违规 0xC0000005、栈溢出 0xC00000FD、堆损坏 0xC0000374 …… |
| `std::set_terminate` | 异常逃出线程函数（未捕获 C++ 异常） |
| `signal(SIGABRT)` | `abort()` / `qFatal()` / 断言失败 |

产物落在 `logs/crashdumps/LRConvert-crash-<时间戳>-<pid>.dmp`，
同时在日志里留下异常代码、原因和 dmp 路径。

## 9.1 踩到的三个坑（都是实测出来的）

**坑 1：不挂 SIGSEGV/SIGFPE/SIGILL 的 signal handler。**
访问违规在 Windows 上本质是 SEH。挂了 signal handler 会被 CRT **抢先接走**，
那条路拿不到 `EXCEPTION_POINTERS`，dump 没有异常现场。
只挂 `SIGABRT`（abort 不走 SEH），其余交给 SEH 过滤器。

**坑 2：不能在异常分发回调里直接写 dump。**
`sehFilter` 跑在崩溃线程的异常帧上，进程仍处于"异常未处理"状态，
此时 `LoadLibrary(dbghelp)` + `MiniDumpWriteDump` 会失败 ——
**文件被创建出来却是 0 字节**，比没有更误导人。
标准做法是**另起一个线程**去写：崩溃线程在 `WaitForSingleObject` 上保持不动，
它的寄存器和栈正好被 dump 线程抓进 .dmp。

**坑 3：dbghelp 要在安装时就加载好。**
崩溃时再 `LoadLibrary` 能不能成全看运气。改成 `installCrashHandler()` 里
预加载并缓存 `MiniDumpWriteDump` 函数指针（句柄故意不释放，留到进程结束）。
就这一条，dump 从"0 字节"变成"164 KB"。

顺带修掉一个真 bug：`MINIDUMP_EXCEPTION_INFORMATION::ThreadId` 必须填
**发生异常的那个线程**的 ID。早先在 dump 线程里填 `GetCurrentThreadId()`，
拿到的是 dump 线程自己的 ID，配上崩溃线程的 `ExceptionPointers`，
`MiniDumpWriteDump` 直接报 `ERROR_NOACCESS(998)`。

## 9.2 已知限制

异常现场（`ExceptionPointers`）最终没能写进 dump —— 三级降级跑到了第 3 档，
即**只有各线程的调用栈**，用 VS 打开不会自动停在崩溃那一行。
日志里会明确提示这一点，避免事后对着 dump 白费功夫。
补偿是日志里有精确的异常代码（如 `0xC0000005`）。

三级降级：① 带现场 + 线程信息 → ② 带现场、基础信息 → ③ 不带现场（仅线程栈）。

## 9.3 自检钩子

```bash
LRCONVERT_CRASH_TEST=1 ./build/LRConvert.exe    # 1.5 秒后故意制造一次访问违规
```

正常运行时这个环境变量不存在，永远不会走到。留着它，是为了换机器/换编译器后
还能一键确认转储链路没失效。

## 11.2 新增/改动的模块

**`platform/ThreadUtil`（P1-6 / P2-12）**

- `setThreadName()`：动态取 `SetThreadDescription`（Win10 1607+）。
  早期版本还留了一条 `0x406D1388` 的兜底，因为那套约定必须包在 MSVC 的
  `__try/__except` 里才安全（没人接住时它是个真异常），MinGW 只有变体语法 ——
  **为一个调试便利引入方言不值得**，去掉了；拿不到名字就只是少个名字。
- `BigStackThread`：`_beginthreadex` 起线程并显式给 8MB 栈（`std::thread` 在
  Windows 上固定 1MB，SWR/解码那条深调用链上栈溢出是真风险）。
  接口刻意做得跟 `std::thread` 一样薄（`joinable`/`join`/可移动），方便原地替换。
- `runWithTimeout()`：给"可能卡住又不能拖死流程"的调用用（硬件编码器探测）。
  **契约**：超时返回 false 时函数可能还在后台跑，所以回调必须是自持状态的
  —— 这也是 FfmpegCapability 里改用 `shared_ptr` 存探测结果的原因。

**`ffmpeg/IoTimeout`（P0-4）**

`AVFormatContext.interrupt_callback` + **thread_local 截止时间**。用 thread_local
而不是塞进回调 opaque，是因为敲回调的线程跟阻塞读的线程是同一个，
生命周期天然安全；截止时间按"每次 I/O 现 ARM、完事即 DISARM"，
避免给一个长生命周期的 context 挂上过期语义。

**`ffmpeg/FfObjects`（P2-11）**

`FfPtr<T>` + 每实例一个释放函数指针。头文件只前向声明 libav* 类型，
释放逻辑集中在 `FfObjects.cpp` 一个文件 —— 保住了"不链接 libav*"的既有架构。
`FrameGrabber` / `AudioDecoder` / `AudioPeaks` / `MediaProbe` / 两个 Task 全改过：
错误分支从"手工配平四五次释放"变成直接 `return false`，
异常路径（P2-9）也不用再逐个补清理。

两个体的接管/释放坑（都踩过）：

- `sws_getCachedContext` 会接管（甚至释放）旧上下文 → 先 `release()` 交出所有权，
  再拿返回值 `reset()`，否则双重释放；
- `swr_alloc_set_opts2` 是**出参**模式 → 先拿裸指针，成功后再 `reset()` 接管。

## 11.3 任务管线：异常收敛 + 原子落盘（P2-9）

`TranscodeTask` / `RemuxTask` 的主体各包一层 try/catch：任务线程是 `std::thread`
语义，异常飞出去就是 `std::terminate` —— 进程消失，dump 都未必写得出来。

输出改成 **临时文件 → 关闭句柄 → rename** 三步：

```
<原名>.LRConvert-tmp.mp4   ← 实际写入
        ↓ avio_closep()
        ↓ std::filesystem::rename
<原名>.mp4                  ← 最终路径
```

**踩到的坑（回归 A 组全红才暴露）**：mp4 的 `movflags +faststart` 会在写文件尾时
按容器里记的 url **重新打开一次**这个文件（把 moov 挪到文件头）。
第一版把 `avformat_alloc_output_context2()` 指给最终路径、只把 `avio_open` 换成
临时文件，于是这一步 reopen 打到还不存在的最终路径上：
`Unable to re-open ... for shifting data` → `moov atom not found`。

修法：**容器也按临时路径建**，且临时文件名必须**保留原后缀**
（`pathutil::atomicTempPath()`）—— 后缀一改，推断出来的封装器就是错的。
（写成 `原名.mp4.LRConvert-tmp` 是不行的，就是吃了这个亏。）

顺带统一了两个概念的分离：`ok`（任务算不算成功）与 `keepOutput`（文件留不留）。
手动停止时两者分叉 —— 任务失败，但已经写好的那半截文件按原行为保留。

## 11.4 崩溃 → 下次别再踩（P1-8）

判定不靠解析系统日志，也不在崩溃路径上做额外 I/O：

- 每次**正常退出**写/刷新一个空标记 `logs/crashdumps/clean-exit.marker`；
- 启动时拿它的时间戳与目录里最新那份 `.dmp` 比 —— 标记更旧 = 上次没走到正常退出；
- 命中就在这一跑跳过**硬件编码器探测**（这条链路要打开各家厂商驱动，
  是环境差异最大、最不稳的一段），并在界面与日志里说明原因。

用户看到的是一句人话（"上一次运行似乎没有正常结束…本次已启用安全模式"），
而不是"下拉框里少了几项硬件编码器"这种哑谜。干净退出一次之后自动恢复。

## 11.5 仍然存在的边界（如实记录）

1. **网络盘 / SMB**：本地文件的读不走协议轮询，`interrupt_callback` 不会被查询，
   所以"共享盘掉线"这种阻塞发生在 OS 层，回调管不到。
   补偿是**打开之前**用重叠 I/O 做一次可读性探测（带超时），
   加上看门狗兜底 —— 但真到了"读到一半网卡被拔"，仍然要等到 OS 本身超时。
2. **原子落盘不能救"输入=输出"**：rename 的目标被输入句柄占着，所以开跑前就拦下来
   （`pathutil::sameFilePath`）。
3. **WER LocalDumps 需要关机时时清爽**：注册表写在 HKCU，不需要管理员权限；
   但只对按 `LRConvert.exe` 进程名启动的有效（`logs/crashdumps/wer/` 子目录）。
4. **Mutex 等待不是无限的**：GUI 线程的冒烟查询仍然会等取帧器锁，
   但那把锁现在是 `timed_mutex`，且取帧任务有时限（60ms 抢不到就放弃这一拍），
   等待期是有界的。

# 稳定性排查与加固（2026-10-15）

起因：用户测试时遇到一次**程序突然退出**，要求排查代码健壮性，
特别是"音视频解码错误导致的退出"，并给出进一步增强稳定性的建议。

本文记录：排查了哪些地方、发现了什么、修了什么、还剩哪些建议。

---

## 1. 最可能的元凶：从 worker 线程直接操作 UI

**位置**：`MainWindow::setupTimeline()` 里给 `waveBuilder_` 设的两个回调。

`WaveformBuilder` 用的是 **`std::thread`**（4 个 worker），不是 `QtConcurrent`。
它的 `progressCb_` / `errorCb_` 是在 **worker 线程**里被调用的，而回调体里写了：

```cpp
if (timeline_) timeline_->update();        // QWidget，只能 GUI 线程碰
appendLog(...);                            // 直接操作 infobox（QTextEdit）
rebuildCutWaveform(cutToken_);             // 读 UI 状态 + 再起后台任务
```

Qt 的规则是**任何 QWidget 都只能在 GUI 线程使用**。从后台线程调 `update()` /
`insertHtml()` 是未定义行为：绝大多数时候看起来没事，偶发就是直接崩，
而且崩在哪一行、什么时机完全随机 —— 正好对应"用着用着突然没了"这种症状。

**为什么之前没暴露**：时序巧合。波形算得快的时候，那几行可能正好赶在
GUI 线程空闲时执行完；一旦同时有别的任务占用（比如正在解码、正在取缩略图），
Qt 内部的状态就可能对不上。

**修法**：两个回调的 lambda 本体一行都不碰 UI，全部
`QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 丢回 GUI 线程再做，
并带 `QPointer` guard + token 校验。

> 顺带核对过：其余 8 处 `QtConcurrent::run` 的后台块都是干净的
> （只做计算，UI 操作都走 `invokeMethod`），就这一处是 `std::thread` 漏了。

## 2. 第二个元凶：播放时帧回调没有背压

播放线程每解一帧就 `QMetaObject::invokeMethod` 投一个含 `QImage` 的 lambda 给
GUI 线程。GUI 一忙（比如同时有 4 个线程在算整轨波形），**这些事件会排起队来**。

一张 1080p 的 `QImage` = 6 MB。积压几十帧就是几百 MB，几百帧就是上 GB ——
结局不是卡死就是被系统杀掉，而用户看到的只是"程序突然没了"。

**修法**：`pendingFrames_` 原子计数，投递前 +1、GUI 线程执行时 −1，
待处理 ≥ 3 帧就直接丢掉这一帧。**播放宁可掉帧，也不能让内存失控。**
`stopPlayback()` 里归零，且计数减到 0 就夹住不让它变负
（否则下一轮播放要白丢好几帧才恢复正常）。

## 3. 线程里的异常 = 进程直接消失

`FramePlayer::threadMain` 和 `WaveformBuilder::workerMain` 都**没有 try-catch**。
解码、sws 缩放、`std::vector` 分配都可能抛异常（损坏文件、异常分辨率、内存不足）。
异常一旦逃出线程函数，C++ 运行时直接 `std::terminate()` —— 整个进程瞬间消失，
**没有日志、没有崩溃对话框、没有任何提示**。这跟用户描述的"退出"完全吻合。

**修法**：两个线程入口各包一层 `try { ... } catch (...) { ... }`，
捕获后安静地按"播完了/这段不算了"处理。

## 4. 其余修掉的隐患

| # | 位置 | 问题 | 修法 |
|---|---|---|---|
| 1 | `MainWindow::toQImage` | 只查了 `rgb.empty()`，没校验数据量；尺寸对不上就是**越界读** | 校验 `rgb.size() >= w*h*3`，并限制最大 16384×16384、`image.isNull()` 也判掉 |
| 2 | `FramePlayer::close()` | 不先 `stop()` 就释放 `video_`/`audio_`，播放线程还在用它们 → **use-after-free** | `close()` 开头先 `stop()` |
| 3 | `FramePlayer::pumpAudio` | 音频包无时间戳时 `startSec = -1`，`audioSec_` 变负、循环永不退出，**一口气读完整个文件** | 无时间戳时按"接上一段"估算；并加 512 次硬上限 |
| 4 | `AudioDecoder::decodeNext` | swr 输出未钳制，`produced` 超预期会写穿缓冲区 | `used += std::min(produced, space)` |
| 5 | `FrameGrabber::decodeNext` | 损坏文件时坏包循环会一直读到文件尾，界面不崩但 CPU 跑满 | 连续 300 个坏包就放弃并报错 |
| 6 | `FrameGrabber::grabAt` | seek 失效/时间戳乱掉时会一路解到文件尾（长视频几万帧） | 1500 帧上限，超限用已拿到的最后一帧 |
| 7 | `FrameGrabber::convertFrame` | 异常分辨率让 `resize` 抛 `bad_alloc` | 尺寸合法性 + 上限检查 |
| 8 | `MainWindow::applySnappedRange` | 吸附把区间吸反了（关键帧稀疏/损坏文件时真的会）**只打日志，照样把倒挂区间写回去** → 目前时长负数、可拿负区间去编码 | 检测到倒挂就保持原选择不变 |

第 8 条是**用损坏文件实测出来的**：污染视频的关键帧表异常，吸附后变成
`起点=5.000 终点=2.000`。修完变成保持 `2.300 ~ 4.700` 原值。
（`cutFile()` 本来就有 `end <= start` 的校验兜底，所以不会真的去编码。）

## 5. 加上的诊断能力：日志落盘 + FFmpeg 报错接入

这次"不知道是什么原因"，下次就得能查。

- **程序日志**：`main.cpp` 装 `qInstallMessageHandler`，所有 Qt 日志写一份到
  `logs/LRConvert.log`（exe 同级；写不进去就退回系统临时目录）。
  超过 2 MB 重新来一份。**每条立即 `fflush`** —— 崩了也要留下最后那几行，
  而那往往正是最接近现场的部分。
- **FFmpeg 自己的报错也接进来**：新增 `FfmpegApi::setLogSink()`，
  把 `av_log_set_callback` 桥到程序日志。解码器抱怨了什么、哪个流坏了、
  硬件编码器为什么不可用，以前只飘在 GUI 程序看不见的 stderr 里，现在进日志文件。

  ⚠ **这里有个坑**：FFmpeg 的 `av_vlog()` 拿到回调**直接就调**，
  级别过滤只存在于它的默认回调里。自定义回调必须自己判断 `level`，
  否则硬件探测那堆 `Loaded lib: nvcuda.dll` 会全涌进来 ——
  实测一次启动刷出 **56083 条**。
- **限流**：坏文件会源源不断报同一个错，前 100 条照实记，之后每 100 条汇总一次。
  修完 56083 → **156 条**，日志 21 KB。
- **`app.exec()` 兜底**：包 try-catch，真漏出异常时弹框说明 + 写日志，
  而不是 `std::terminate()` 静默消失。

## 6. 验证

| 项目 | 结果 |
|---|---|
| 正常片冒烟 | 波形 2400 点 / 16 段、翻页、拖滑块停播全部正常 |
| 损坏文件 × 3（截断 / 数据污染 / 仅剩头） | **退出码均为 0**，无崩溃；污染片导入成功、波形算完、区间不再倒挂 |
| 一键回归 | **12/12 通过** |
| 日志 | 落盘正常，含 FFmpeg 错误与抑制计数 |

三种损坏文件是临时生成的（截断到 45%、中间 40% 字节填 0xFF、只留 12%），
验证完已删除。

## 7. 还没做的进一步建议

按性价比排序，都不是必修，视需要再上：

1. **崩溃转储**：装 `SetUnhandledExceptionFilter` 在崩溃时写 minidump。
   上面加的 try-catch 只能拦 C++ 异常，**拦不住空指针解引用、栈溢出、堆损坏**
   这些 Windows SEH 层面的错误 —— 那类问题只能靠 dump 定位。
2. **日志按天轮转 + 保留最近 N 份**：现在只按 2MB 截断，长期用会覆盖历史。
3. **播放与波形错峰**：导入后的头几秒 CPU 是打满的（4 worker + 解码）。
   可以让波形在播放开始后自动降优先级（减到 1~2 个 worker）。
4. **长视频内存上限**：现在是 400 点/秒，2 小时视频 = 288 万点 ≈ 5.8 MB，
   可以接受；但若将来提高密度，要给 `allocate()` 加总量上限。
5. **硬件编码器探测超时**：探测 nvenc/qsv/amf 是在后台线程做的，
   个别驱动上可能卡住，建议加超时（目前没观察到）。
6. **`FramePlayer::stop()` 的 join 无超时**：理论上播放线程一定会在
   一帧时间内退出（最坏等一个 `write` 的 40ms 超时），暂不需要；
   若将来在循环里加了更长的阻塞操作，就得给 join 加上限。
